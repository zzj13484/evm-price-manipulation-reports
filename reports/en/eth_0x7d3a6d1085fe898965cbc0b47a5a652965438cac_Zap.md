## Summary

`Zap` routes multi-step conversions among YB / yYB / st-yYB / LP / YBS / veYB through an immutable **Curve `POOL`**. Pricing uses instantaneous **`get_dy` / `calc_withdraw_one_coin` / `get_virtual_price`** — no TWAP or external oracle.

User entry **`zap(..., minOut, ...)`** checks **`minOut` only on final output**, while internal Curve calls set **`min_dy` / `_min_amount` / `_min_mint_amount` to `0`** — equivalent to Router **`amountOutMin = 0`**. Attackers manipulate Curve reserves in one block, force bad fills on `exchange` / `remove_liquidity_one_coin` / `add_liquidity`, then reverse trade.

Source **`calcExpectedOut`** notes *"subject to manipulation if used on chain"*; the on-chain **`zap`** path remains exposed on intermediate steps.

**Etherscan:** https://etherscan.io/address/0x7d3a6d1085fe898965cbc0b47a5a652965438cac

## Affected scope

| Component | Role |
|-----------|------|
| `Zap` | User entry; unlimited approvals to POOL / YYB / vaults |
| `POOL` (Curve) | Pricing and execution surface |
| `YYB` | `_convertYb` may `mint` 1:1 when pool quote unfavorable |

**Functions:** `zap` (trigger) → `_convertYb`, `_convertToOutput`, `_addLiquidity`, `remove_liquidity_one_coin` (sinks).

**Not applicable:** Uniswap `slot0`, `_transfer` → `swapAndLiquify`, QU!D/Vogue templates.

## Root cause

### Trigger vs sink

| Template | Zap implementation |
|----------|-------------------|
| Outer trigger | `zap` (routing only) |
| Composite settlement | `_convertYb` + `_convertToOutput` |
| Swap min=0 | `ICurvePool.exchange(i, j, dx, 0)` |
| Add liquidity min=0 | `add_liquidity(_amounts, 0, ...)` |
| Single-coin withdraw min=0 | `remove_liquidity_one_coin(..., 0, ...)` |

```solidity
function _convertYb(uint256 amount) internal returns (uint256) {
    uint256 outputAmount = ICurvePool(POOL).get_dy(0, 1, amount);
    if (outputAmount > amount + (amount * mintBuffer / 10_000)) {
        return ICurvePool(POOL).exchange(0, 1, amount, 0);  // min_dy = 0
    }
    IYToken(YYB).mint(amount, address(this));
    return amount;
}

function _addLiquidity(uint256[] memory _amounts) internal returns (uint256) {
    return ICurvePool(POOL).add_liquidity(_amounts, 0, address(this));
}
```

Manipulating `get_dy` forces victims into high-slippage `exchange` or economically wrong `mint` branch.

## Attack scenario

1. Manipulate Curve pool reserves (flash loan).
2. Victim calls `zap`; intermediate steps accept zero min constraints.
3. Attacker reverse-trades; captures slippage revenue.

Single-block atomicity supported.

## Impact

| Dimension | Assessment |
|-----------|------------|
| **Financial** | User/protocol tokens exit at distorted Curve rates |
| **Integrity** | Multi-hop zap integrity broken despite final `minOut` |
| **Availability** | Repeatable until per-step mins added |

**High severity:** Permissionless user entry; all intermediate Curve sinks unprotected.

## Proof of concept

1. Fork mainnet; bind `Zap` and `POOL`.
2. Record fair `get_dy` quote.
3. Manipulate pool; call `zap` with representative path.
4. Compare intermediate and final outputs vs unmanipulated fork.

## Recommendations

1. Propagate slippage bounds to **each** Curve call from TWAP or oracle-derived quotes.
2. Revert when spot vs TWAP deviation exceeds threshold before `_convertYb`.
3. Do not rely on final `minOut` alone for multi-hop paths.
4. Consider pausing `zap` on abnormal `get_virtual_price` moves.
